# Purchase order changes

## Business behavior

- Create always starts Pending with zero received quantity. Received quantities are maintained by goods receipt posting/reversal, not PO input.
- Supplier, warehouse, product, ordered UOM and base UOM must exist, be active, not deleted, and belong to the PO company. Non-base purchase UOMs require an active positive conversion to base UOM.
- Global EF company filters still govern visibility. Explicit company comparisons validate document relationships for users who can see multiple companies.
- Existing line IDs must be unique and refer to active lines on this PO. Null/zero IDs mean new lines; negative IDs are invalid.
- Received lines cannot be removed, change product/UOM, or reduce ordered quantity below received quantity.
- Total is calculated from final active lines. Quantities support four decimal places, unit prices two; total uses two-place rounding away from zero.
- Fulfillment status is derived from active lines on update. Cancelled POs cannot be edited.
- Supplier changes and PO deletion are blocked while active receipts exist.

## API/client changes

- Create input: supplierId, warehouseId, orderDate, expectedDate, items, idempotencyKey (nonempty UUID).
- Update input: id, supplierId, warehouseId, orderDate, expectedDate, items.
- PO number, status and receivedQuantity are output fields, not editable inputs.
- The client keeps one create key for the open create form, including network retries. Identical replay returns the existing PO; a different payload or deleted PO cannot reuse the key.
- PO numbers are generated by a SQL Server sequence: `PO-2026-00000001`. The sequence is global and does not reset yearly. Gaps after rollback are normal; numbers are not reused or editable.
- Cancellation: `POST /api/process/purchase-orders/{id}/cancel`, body `{ "id": "...", "reason": "..." }`. A trimmed reason of 1–500 characters is required. Only unreceived POs can be cancelled. Repeated cancellation succeeds without replacing the first reason.
- The UI displays number/status as read-only and provides a separate cancellation dialog.

## Concurrency

SQL Server transaction-owned application locks serialize create retries and PO updates, cancellation, deletion, receipt creation, and receipt reversal for the same PO. Create uses ReadCommitted with a per-key lock and sequence; other mutations retain Serializable isolation. Locks expire with transaction completion. This protects received quantity invariants, but is not a browser edit-version token: unrelated header changes from stale forms can still overwrite a newer header edit.

## Schema rollout

Apply `HardenPurchaseOrders` and `AddPurchaseOrderNumberSequence` with EF Core 10 tooling against the intended database after backup/review. These migrations were tested on a disposable database, not applied to the application database during this task.

```powershell
dotnet ef database update --project src/InventoryManagementSystem.Infrastructure --context InventoryManagementDbContext
```

The design-time factory reads `IMS_DESIGN_CONNECTION`. Set it to the intended connection using your secret management mechanism; its fallback is a separate `InventoryManagementDesign` database, not the application database. Never commit credentials.

The first migration fails explicitly if existing company PO numbers are duplicated; reconcile those records before applying it. The second starts the sequence above existing numeric PO suffixes, including deleted documents. Deploy the updated API and client together because input contracts changed.

## Verification

```powershell
dotnet build src/InventoryManagementSystem.slnx --no-restore
dotnet run --project tests/InventoryManagementSystem.PurchaseOrderChecks
dotnet run --project tests/InventoryManagementSystem.CsrfChecks
cd src/InventoryManagementSystem.Client
node node_modules/@angular/cli/bin/ng.js build --configuration development
```

The PO checks use Windows integrated authentication on the local default SQL Server instance. They create a uniquely named `IMS_PO_Checks_<UUID>` database, test the new migrations and real handlers (including receipt posting/reversal), and delete only that generated database in cleanup. They do not access the application's database or send emails.

The suite covers invalid references, precision/overflow, receipt guards, derived status, cancellation, replay/payload mismatch, company visibility, duplicate numbering, concurrent retries, distinct concurrent creates and concurrent receipt/quantity reduction.

## Production work beyond these fixes

Approval/maker-checker policies, action-specific permissions, edit-version conflict handling, revision history, currency/tax/payment-term workflows, partial-order closing, and posting-only document deletion rules need separate business requirements and implementation. These fixes alone do not certify the full ERP as production-ready. The existing generic API exception handling also needs a safe response policy for database lock timeouts/deadlocks.
